# 研序 Yanxu vNext 产品重构需求文档

更新日期：2026-08-06  
文档状态：产品方向与版本计划已确认，0.2.0 已进入验收  
适用范围：Yanxu 下一大版本产品与架构调整  

## 0. 文档定位

本文是 Yanxu 下一大版本的需求基线，用于统一产品定位、核心流程、角色与团队、能力扩展、执行可靠性和现有系统迁移方向。

现有《一期需求、功能与验收总清单》继续作为一期实现和历史验收记录，不再作为下一版本的产品设计依据；《执行可靠性、质量与记忆改进计划》中关于客观门禁、失败分类、可观测性和有效记忆的原则继续有效，并纳入本文。

本文不是详细技术设计，不指定具体代码结构，不包含代码示例。后续应在本文确认后，另行形成实施计划和数据迁移设计。

## 1. 调整结论

Yanxu 不再继续建设一套由固定 Role、SkillStep、Artifact 契约和复杂模型输出共同驱动的 AI 研发流水线。

Yanxu 调整为本地 AI Agent 工程控制面：第一阶段利用 OpenCode 和 Claude Code 自身的规划、编码和工具使用能力，负责它们不擅长统一处理的项目管理、任务隔离、执行生命周期、客观验证、并发、恢复、交付、能力装载和项目记忆；Codex 等其他 CLI 在双 CLI 主线稳定后再适配。

下一版本的产品主张是：

> 用户确认任务计划后，Yanxu 能让合适的本地 Agent 在隔离环境中持续执行，遇到失败可观察、可恢复、可定点修复，最终提供真实可验收的交付结果与证据。

## 2. 现状分析

### 2.1 已有基础

当前项目已经具备以下可继续使用的基础能力：

- 本地 Daemon、Web 工作台、SQLite 和 ProjectSpace 分层。
- 一个项目关联一个或多个本地目录，目录可以是代码、文档、已有 Git、非 Git 或空目录。
- TaskVersion、PlanVersion、Run Snapshot、ProjectSpace Git 版本和事件证据链。
- Git branch 与 worktree 任务隔离，不同任务可并行执行。
- CLI 探测、模型配置、AI 人员、团队和全局默认团队。
- OpenCode 真实执行适配；Claude Code 和 Codex 已有探测与扩展入口。
- 任务计划确认、暂停、停止、恢复、租约回收、失败分类和重试基础。
- 质量门禁命令执行、退出码、超时、日志、评审 Finding 和交付报告。
- 任务诊断、运行日志、变更清单、文件 Diff、权限请求和冲突处理。
- ProjectSpace 完整性、恢复清单、项目知识候选、修订、失效和检索。

以上能力构成 Yanxu 的真正产品资产，应优先保留和强化，而不是随流程重构推倒重写。

### 2.2 当前模型的主要问题

当前实现以 Role、Skill 和 SkillStep 为中心：

- Skill 直接绑定唯一 Role。
- Role 通过 Skill 列表决定能够参与哪些步骤。
- 团队通过 Role/Skill 覆盖情况判断任务可执行性。
- 计划步骤必须选择 Skill，并分配拥有该 Skill 的人员。
- 每个 Skill 声明固定 Artifact 类型和完成检查。
- 每个 SkillStep 要求模型返回复杂结构化结果。
- 调度器需要理解不同 Skill 的特殊规则，并据此推进状态。

这种设计产生了以下结果：

1. 流程复杂度持续增长。每增加一个任务类型、角色或 Skill，都需要新增产物、Schema、校验、提示词和状态处理。
2. 模型容易优先满足输出格式，而不是解决真实问题。当系统强制“必须有文件改动”或“必须生成某类 Artifact”时，Agent 可能生成无价值报告来满足契约。
3. 模型自报成功与真实结果可能不一致。真实任务中已经出现模型声明成功，但项目测试仍有失败的情况。
4. 固定角色与 Skill 关系限制了自由组合。任务需要的是能力，却被转换为“必须加入某个角色”。
5. 每个 SkillStep 使用独立会话会增加上下文损耗、重复阅读和 Token 消耗，也不利于失败后在原思路上继续修复。
6. 失败处理容易退化为从前序步骤重新开始，而不是围绕当前失败证据定点修复。
7. 编排器逐渐承担模型思考、角色安排、产出裁决和失败决策，形成新的黑盒。

### 2.3 本次调整不否定的内容

本次重构不否定需求计划、角色团队、Skill、测试、评审和项目记忆的价值。需要调整的是它们在系统中的位置：

- 需求计划继续存在，但由用户确认目标、范围、分配、能力和验证方式，不规定 Agent 的思考过程。
- 角色和团队继续存在，但作为可复用执行资源，不作为固定流程节点。
- Skill 和 MCP 继续存在，但作为可装载能力，不作为工作流状态机。
- 测试和评审继续存在，但客观检查由系统执行，是否需要独立 AI 评审由任务风险决定。
- 文档和 Artifact 继续版本化，但只在任务确实需要时产生，不再要求每一步必须生成。
- 项目记忆继续沉淀，但只接纳已确认、可追溯和当前有效的事实与经验。

## 3. 产品定位与边界

### 3.1 产品定位

Yanxu 是面向本地项目的多 Agent 工程控制面，核心职责包括：

- 管理项目、项目目录、多仓库信息和独立 ProjectSpace。
- 接收需求，调用规划 Agent 形成可确认计划。
- 管理 AI 人员、角色模板、团队和任务分配。
- 发现、管理并按任务装载 Skill 与 MCP。
- 为任务准备隔离 Git 工作区和独立 CLI 运行环境。
- 管理 CLI Session 的创建、持续执行、暂停、恢复、终止和重试。
- 收集日志、事件、工具调用、文件变化、权限、失败和交付证据。
- 在真实任务工作区执行确定性质量门禁。
- 将失败证据返回原 Session，推动当前失败环节修复。
- 形成分支、变更、验证结果和风险清单，交由用户确认交付。
- 将用户确认后的项目事实、决策和经验沉淀到 ProjectSpace。

### 3.2 非目标

下一版本明确不以以下内容为目标：

- 不自行实现一个替代 Claude Code、OpenCode 或其他编码 CLI 的通用 Agent。
- 不用大量提示词和输出契约控制 Agent 的完整思考过程。
- 不规定所有研发任务都必须经过产品、研发、测试、评审四类角色。
- 不要求每个步骤必须生成固定文档或 Artifact。
- 不以模型返回的成功状态作为测试通过或任务完成的依据。
- 不在第一阶段建设完整 Skill 市场、评分体系或社区生态。
- 不在第一阶段支持同一任务内部的复杂并行依赖图；不同任务继续支持并行，同一任务先保持可理解的串行工作单元。
- 不因能力扩展而默认修改用户所有 CLI 的全局配置。

## 4. 产品原则

### 4.1 确定性控制，Agent 自主执行

任务状态、进程、超时、工作区、权限、退出码、重试边界和交付由程序控制；需求理解、方案设计、编码、失败分析和评审判断由 Agent 完成。

### 4.2 任务需要能力，不直接需要角色

任务计划声明需要的能力，系统从已选团队中推荐合适人员。角色是能力和行为的默认模板，不拥有能力的排他权。

### 4.3 客观证据优先

文件变化以 Git 为准，质量结论以真实命令和退出码为准，Session 状态以进程与运行协议为准。模型说明只作为解释和建议，不能覆盖客观失败。

### 4.4 隔离优先于全局同步

任务运行时所需 Skill、MCP、规则和凭据引用，应优先装载到任务或项目独立环境，不能通过频繁改写全局 CLI 配置影响并行任务。

### 4.5 人工确认集中在关键决策点

默认人工卡点是计划确认和最终交付确认。扩大范围、提升权限、增加目录、引入高风险能力、语义冲突或缺少凭据时再请求用户介入。

### 4.6 历史可追溯，当前认知可纠正

需求、计划、能力版本、执行快照、交付和知识均保留版本。错误内容通过 supersedes 和失效状态退出当前检索，不删除历史证据。

## 5. 核心领域概念

### 5.1 项目与 ProjectSpace

- Project 表示用户在 Yanxu 中管理的项目，可以关联多个本地目录。
- 关联目录可以是代码仓库、文档目录、空目录或普通文件目录。
- ProjectSpace 独立于关联目录，用于保存需求、计划、任务快照、证据、能力锁定信息、交付和项目认知。
- ProjectSpace 继续使用独立 Git 记录已知文件的版本变化。

### 5.2 角色模板 RoleTemplate

角色模板描述“以什么职责和工作方式处理任务”，包含：

- 名称、职责、适用场景和基础指令。
- 默认推荐能力。
- 默认权限倾向。
- 来源、版本和兼容信息。

角色模板不直接绑定唯一 CLI 和模型，也不作为流程节点。外部 GitHub 角色导入后首先成为角色模板草稿。

### 5.3 AI 人员 AgentProfile

AI 人员表示“由哪个 CLI 和模型扮演某个角色”，包含：

- 角色模板。
- CLI、模型和模型参数。
- 权限模式。
- 默认能力增补或禁用项。
- 可用状态和运行验证结果。

AI 人员是可复用模板，不是固定占用的席位。每次任务实际使用时创建独立的 Session 和运行快照。

### 5.4 团队 Team

团队是 AI 人员的可复用集合，用于限定本次任务可优先选择的执行资源。

- 创建任务时必须指定团队；可以设置一个全局默认团队。
- 团队不代表固定流水线，也不要求所有成员参与。
- 团队不通过“覆盖全部内置 Skill”判断是否完整。
- 任务计划根据能力、CLI 兼容性、模型和权限推荐实际参与人员。
- 任务需要团队外人员时，必须在计划确认前显式提示并由用户决定。

### 5.5 能力 Capability

能力表示可以装载给 Agent 的可复用扩展，第一阶段包括：

- Skill：指令、工作方法、脚本和相关资源。
- MCP：Agent 可连接的工具或数据服务定义。

能力具有来源、版本、内容哈希、兼容 CLI、依赖、权限需求、安装状态、项目启用状态和任务装载状态。

角色可以拥有默认能力，但任务可以为合适的人员临时装载额外能力。任何 Skill 不再绑定唯一角色。

### 5.6 工作单元 WorkUnit

工作单元是计划中的可执行目标，替代当前以 Skill 为中心的 SkillStep。工作单元描述：

- 要完成的目标。
- 涉及的项目目录和范围。
- 所需能力。
- 推荐或确认的执行人员。
- 前置依赖。
- 验证方式。
- 是否要求独立 Session 或独立评审。

工作单元不要求固定 Artifact 类型，也不要求每个单元都修改文件。需要留档的文档由计划明确列出。

### 5.7 运行快照 RuntimeSnapshot

计划确认后冻结本次运行使用的：

- 需求版本和计划版本。
- 项目目录、来源分支、目标分支和基准提交。
- 团队、人员、角色模板。
- 能力版本和任务装载配置。
- 权限、禁止路径和质量门禁。
- CLI、模型和运行参数。

运行中的配置变化不能影响已经确认的任务。

## 6. 新核心流程

### 6.1 需求提交

用户选择项目和团队，提交需求、期望结果、约束、附件和目标分支信息。系统校验项目、团队和至少一个可用执行 CLI，但此时不要求团队覆盖固定角色或 Skill。

### 6.2 项目理解与计划生成

规划 Agent 读取有界项目事实、相关文件、当前有效知识和用户附件，生成：

- 目标、范围、非范围和成功标准。
- 涉及的目录、仓库和分支。
- 工作单元及其验证方式。
- 每个工作单元需要的能力。
- 推荐执行人员及推荐原因。
- 需要临时装载的 Skill/MCP。
- 权限清单和质量门禁。
- 风险、假设和歧义问题。

计划正文使用便于用户阅读和修改的 Markdown；状态流转只依赖少量稳定的结构化字段，不再要求规划 Agent生成复杂的全流程产物契约。

### 6.3 歧义处理与人工确认

每个关键歧义应提供一个推荐方案和若干可选方案，同时允许用户自定义回答。用户回答后，规划 Agent 必须把答案吸收到新版计划中。

确认页面必须明确展示：

- 改什么、不改什么、如何验收。
- 哪些目录和分支会被使用。
- 哪些人员实际参与，分别负责什么。
- 哪些能力是角色默认能力，哪些是任务临时装载。
- 哪些权限、命令、网络和依赖安装行为被允许。
- 是否存在能力缺口、CLI 不兼容或必须独立评审的情况。

用户确认后生成 RuntimeSnapshot，任务进入准备阶段。

### 6.4 执行准备

系统为每个涉及目录创建任务分支和隔离工作区，冻结基准状态，并为每个将参与的 Agent 准备独立 Session 环境。

系统按 RuntimeSnapshot 将需要的 Skill、MCP 和规则投影到任务运行环境。能力装载失败、凭据缺失或 CLI 不兼容时不得静默降级，应在执行前阻塞并给出可处理原因。

### 6.5 Agent 执行

- 不同任务可以并行运行。
- 同一任务第一阶段按确认后的工作单元串行推进。
- 同一人员连续处理相关工作单元时，优先复用同一 Session。
- 发生质量失败时，优先把失败证据返回原 Session 修复。
- 只有切换人员、要求独立评审、原 Session 不可恢复或用户明确要求时，才创建新 Session。
- Agent 可以自主阅读授权工作区、修改文件和执行已批准命令，不要求每一步返回固定文档。
- Agent 需要扩大目录、权限、目标或成功标准时，任务进入重新确认，而不是自行扩展。

### 6.6 系统验证

执行完成后，Yanxu 在任务实际工作区、同一项目依赖和同一项目级工具链中运行确认的质量门禁。

- 质量门禁只信任真实命令、退出码、信号、超时和日志。
- 不允许在依赖缺失时回退到无关的系统全局工具并形成误导结论。
- 模型返回“成功”但质量门禁失败时，任务不能进入交付。
- 失败证据应精确包含命令、目录、退出码、日志摘要和相关文件。
- 系统将证据返回当前执行 Session，重试当前失败工作单元或验证环节。
- 重试不得默认回到任务第一个实施步骤。

### 6.7 交付与归档

质量满足确认标准后生成交付结果，包括：

- 完成情况和未完成项。
- 实际变更目录、文件和提交。
- 质量门禁结果和日志证据。
- 独立评审意见和剩余风险。
- 任务分支、目标分支和合并选项。
- 任务使用的人员、模型和能力版本。

用户可以选择自行合并或由 Yanxu 合并到任务指定的目标分支。用户确认完成后任务归档，随后生成项目知识候选。

## 7. 明确功能需求

### 7.1 产品与流程需求

- [ ] `VNX-FLOW-001` 新任务不再生成固定 SkillStep 序列，改为基于需求生成 WorkUnit。
- [ ] `VNX-FLOW-002` WorkUnit 不要求绑定 Skill，允许仅声明目标、执行人员、能力需求和验证方式。
- [ ] `VNX-FLOW-003` 不要求每个 WorkUnit 生成 Artifact；只有计划明确要求的需求、设计、报告或交付文档才版本化保存。
- [ ] `VNX-FLOW-004` 计划确认继续作为默认人工卡点，确认前可以修改需求、范围、人员、能力、权限、分支和门禁。
- [ ] `VNX-FLOW-005` 任务执行中必须支持暂停、恢复、立即停止、终止废弃和重新打开。
- [ ] `VNX-FLOW-006` 不同任务继续支持并行；同一任务第一阶段保持串行执行，避免引入复杂依赖图。
- [ ] `VNX-FLOW-007` 用户确认交付前状态为待交付，确认合并或自行处理后才归档为真正完成。

### 7.2 规划需求

- [ ] `VNX-PLAN-001` 规划 Agent 必须基于实际项目目录、当前代码、项目知识和附件生成计划。
- [ ] `VNX-PLAN-002` 计划必须明确目标、范围、非范围、成功标准、工作单元、目录、分支、权限、能力和质量门禁。
- [ ] `VNX-PLAN-003` 每个工作单元声明所需能力，不直接声明“必须加入某个角色”。
- [ ] `VNX-PLAN-004` 系统根据已选团队推荐人员，并展示推荐理由、临时能力和兼容性。
- [ ] `VNX-PLAN-005` 关键歧义必须提供推荐方案、可选方案和自定义回答入口。
- [ ] `VNX-PLAN-006` 用户回答必须吸收到新版计划；未吸收回答时不能确认。
- [ ] `VNX-PLAN-007` 计划只保留状态机需要的最小结构化字段，避免把模型输出格式当作主要质量保障。

### 7.3 角色、人员与团队需求

- [ ] `VNX-ORG-001` RoleTemplate 与 SkillDefinition 的唯一归属关系必须解除。
- [ ] `VNX-ORG-002` 角色模板只定义职责、基础指令、默认推荐能力和权限倾向。
- [ ] `VNX-ORG-003` AI 人员继续绑定角色、CLI、模型、参数和权限模式，并允许覆盖默认能力。
- [ ] `VNX-ORG-004` 团队只表示可用 AI 人员集合，不要求覆盖产品、研发、测试、评审或全部内置 Skill。

## 8. 状态模型调整

用户可见主阶段收敛为：

1. 草稿。
2. 规划中。
3. 待确认计划。
4. 准备中。
5. 执行中。
6. 验证中。
7. 待交付。
8. 已归档。

异常和控制状态保留：

- 已暂停。
- 待用户处理。
- 已停止。
- 已取消。
- 已重新打开。

重试、恢复、重新规划和权限等待作为当前阶段的原因或子状态展示，避免继续增加大量用户难以理解的顶层状态。内部仍可保留必要技术状态，但必须映射到统一用户阶段。

## 9. 现有系统改进策略

### 9.1 保留并强化

- 项目、多目录和 ProjectSpace。
- SQLite 状态、事件和证据链。
- Git 分支、worktree、脏工作区基线和冲突处理。
- 任务看板、暂停、停止、恢复和取消。
- CLI 探测、Session 记录和运行日志。
- 权限清单、敏感路径和高风险操作边界。
- 质量门禁执行与交付合并。
- ProjectSpace 完整性、恢复和知识版本。

### 9.2 重点重构

- Scheduler：从 Skill 契约驱动改为 WorkUnit、Session 和客观 Gate 驱动。
- Planner：从选择固定 Skill 序列改为生成目标、能力、人员和验证计划。
- Context Pack：从强依赖上游 Artifact 改为围绕当前计划、实际工作区、变更和失败证据组装。
- Team 覆盖检查：从 Skill/Role 覆盖改为能力兼容性和人员可用性检查。
- Role/Skill 数据关系：从唯一归属改为默认推荐与任务临时装载。
- Retry：从完整步骤链重跑改为当前工作单元和原 Session 定点修复。
- 质量裁决：彻底分离模型说明与系统 Gate 结果。

### 9.3 废弃或降级为兼容层

- `SkillDefinition.roleId` 唯一绑定。
- 计划步骤必须分配拥有对应 Skill 的角色规则。
- 每个 Skill 固定 Artifact 类型作为推进条件。
- 每个 Skill 固定 CompletionCheck 由模型逐项自报。
- 每个 SkillStep 默认创建独立 Session。
- “没有文件变化就必须制造产物”的完成要求。
- 模型结构化成功状态直接推进交付。
- 团队必须覆盖内置产品、研发、测试、评审能力的检查。

### 9.4 新增模块能力

- 统一 Capability Registry。
- 本机 Skill/MCP 发现器。
- Claude Code、OpenCode 能力格式适配器，并保留新增其他 CLI 的扩展接口。
- 项目能力锁定与任务能力快照。
- 任务级能力投影和隔离运行环境。
- GitHub、本地目录和 ZIP 扩展导入器。
- 外部角色转换与兼容性判定。
- 基于能力的人员推荐与分配解析。

## 11. 分阶段交付边界

### 阶段一：执行主线回正

目标是证明 Yanxu 作为控制面能够可靠完成一个真实研发任务。

范围：

- WorkUnit 替代新任务的 SkillStep。
- 简化规划和计划确认。
- 团队作为人员候选池。
- OpenCode 单执行适配器主线。
- 同一人员 Session 延续。
- 同工作区真实质量门禁。
- 失败回原 Session 定点修复。
- 现有日志、暂停、恢复、Git 隔离和交付继续工作。
- 历史任务兼容查看。

阶段一不要求第三方扩展市场，也不要求 Claude Code 真实执行。

### 阶段二：统一能力体系

范围：

- Capability Registry。
- 扫描本机 Claude Code、OpenCode 的 Skill/MCP。
- 项目能力启用和版本锁定。
- 任务级能力装载与隔离。
- 标准 Skill 的 GitHub、本地目录和 ZIP 导入。
- MCP 格式转换、凭据引用和基础健康检查。

### 阶段三：双 CLI 与外部角色生态

范围：

- Claude Code 执行适配。
- 常见外部角色格式转换。
- 外部角色依赖能力导入。
- 扩展更新、差异审查和版本迁移。

Codex 及其他 CLI 不属于 vNext 1.0 的必需范围。只有 OpenCode 与 Claude Code 均完成真实任务、Session、权限、能力装载、门禁和恢复闭环后，才按相同适配器边界继续接入。

完整市场、评分、发布和社区团队包不纳入前三阶段的完成条件。

## 12. 核心验收场景

### 12.1 单任务完整闭环

用户在已有项目中提交一个真实功能需求，确认计划后离开。OpenCode 在隔离工作区中完成修改，Yanxu 执行真实门禁并生成可合并交付。全过程不要求用户监控普通步骤。

### 12.2 真实失败定点修复

Agent 声明完成，但门禁存在失败。Yanxu 必须阻止交付，将失败命令和日志返回原 Session。Agent 修复后只重新执行相关验证，不从第一个工作单元重跑。

### 12.3 两个任务并行隔离

同一项目两个任务同时修改相同仓库甚至相同文件，两个任务的分支、worktree、Session、能力配置和日志互不覆盖。后合并任务出现语义冲突时等待用户决定。

### 12.4 团队自由组合

团队只有产品和研发人员时，普通功能任务仍可规划、实现并由系统运行测试，不因缺少测试角色而禁止启动。只有计划明确需要独立测试判断时才提示补充人员。

### 12.5 临时能力装载

任务需要 React Skill，但当前研发角色没有默认携带。系统推荐给兼容研发人员临时装载，不要求新增“前端角色”，用户在计划确认页能够看到并调整。

### 12.6 本机能力发现

系统发现某个 Skill 已安装在 Claude Code 或 OpenCode 中，用户可以查看来源和兼容性，并将其导入统一能力库、启用到当前项目，再装载给兼容任务；原工具配置不被意外破坏。

### 12.7 GitHub 扩展导入

用户粘贴一个 GitHub 地址，系统发现角色和 Skill，展示脚本、权限、依赖和许可证。标准 Skill 可直接形成安装草稿，角色形成 RoleTemplate 草稿；用户确认后加入项目或团队。

### 12.8 项目记忆纠正

用户指出交付理解有误并重新打开任务。新需求和计划形成新版本，旧版本保留但退出当前知识检索；重新交付并确认后才生成新的知识候选。

### 12.9 历史兼容

升级后的 Yanxu 仍能查看一期任务的 SkillStep、Artifact、Session、Gate、Diff 和交付报告，不要求重新执行或迁移历史任务语义。

## 13. vNext 完成定义

vNext 不能以页面存在、Schema 完成或 Fake Executor 通过作为唯一完成依据。至少满足以下条件：

- 新流程不再依赖固定 Skill 序列和强制 Artifact 契约。
- 一个真实 OpenCode 功能任务完成计划确认、执行、真实门禁、失败修复和交付闭环。
- 模型自报成功不能覆盖真实门禁失败。
- 同一任务失败可以在原 Session 和当前工作单元继续处理。
- 两个真实任务可以在同一项目并行且能力配置互不影响。
- 团队缺少非必要角色时不会被错误阻止。
- 标准 Skill 能够从本机或 GitHub 导入、锁定版本并装载到任务。
- 任务执行过程、失败原因、重试动作和交付依据可以由用户直接观察。
- 历史任务和 ProjectSpace 数据保持可读、可恢复和可追溯。
- 自动测试、生产构建和必要人工验收全部通过。

## 14. 风险与控制

### 14.1 过度收缩导致产品只剩 CLI 启动器

控制方式：继续保留项目、计划确认、Git 隔离、并行、恢复、门禁、交付和记忆。这些能力构成控制面价值，不能因简化流程而删除。

### 14.2 能力体系重新膨胀

控制方式：第一阶段只定义 Skill 和 MCP；角色导入只生成模板草稿；市场、评分和复杂包管理延期。能力系统不参与任务状态机。

### 14.3 不同 CLI 配置格式持续变化

控制方式：使用独立适配器和兼容性检测，保存统一事实源与版本；单个适配器失败不影响其他 CLI。

### 14.4 外部扩展带来安全风险

控制方式：导入只读扫描、默认不启用、展示脚本和权限、固定版本、隔离装载、凭据本地引用、运行行为进入审计。

### 14.5 新旧流程并存增加维护成本

控制方式：旧流程只保留历史读取和必要恢复，不继续新增功能；所有新任务在迁移完成后使用 vNext 流程。

## 15. 已确认的产品决策

1. Yanxu 的主线是控制现有 CLI Agent 可靠工作，不是自行替代它们。
2. 规划、编码和评审使用 Agent 能力；状态、隔离、门禁、重试和证据由确定性程序控制。
3. 角色和团队保留，但不再驱动固定流程。
4. 任务声明能力需求，角色只提供默认能力，任务可以临时装载能力。
5. 测试命令由系统执行，不要求每个任务必须有测试角色。
6. Skill 和 MCP 建立统一能力库，参考 cc-switch 的单一事实源和多工具投影思想。
7. 任务运行时优先使用隔离能力配置，不用全局配置切换影响并行任务。
8. GitHub 外部 Skill 可快速导入；外部角色先转换为可审查模板草稿。
9. 质量结论只认真实门禁证据，模型自报不能覆盖失败。
10. 项目记忆只沉淀用户确认、可追溯和当前有效的内容。
11. vNext 1.0 只承诺 OpenCode 与 Claude Code；Codex 在双 CLI 主线稳定后作为后续适配器接入。
