# 故障排查

## 先看哪里

1. “设置 → 系统与存储”：应用/Schema 版本、SQLite、Scheduler、日志路径和恢复点。
2. 任务详情“运行诊断”：当前阶段、失败分类、重试、Session、门禁和最近决策。
3. 统一 Runtime 日志：`~/.yanxu/runtime/tasks/<task-id>/executor/runtime.log`。
4. Daemon 日志：`~/.yanxu/system/logs/daemon.log`。

Daemon 日志超过 10 MB、Runtime 日志在新 Runtime/Session 开始时超过 20 MB 会轮转，默认保留 3 代。

## 页面 404 或白屏

用 `./yanxu` 重新启动，不要直接叠加运行 `node apps/daemon/dist/index.js`。启动脚本会核对 Daemon 锁、健康接口与进程命令，只停止经验证的旧进程，再构建并启动同一版本前后端。

## `better-sqlite3` Node ABI 不匹配

`./yanxu` 会自动对当前 Node.js 运行时重建原生模块。如果仍失败，安装 macOS Command Line Tools，然后重试。不要在不同 Node 版本间共用一个已编译的 `node_modules`而绕过脚本检查。

## CLI 可用但任务不可执行

- 在设置页先“重新检测 CLI”，再执行“验证真实运行时”。
- 检查人员选择的模型是否仍可用，Role 和 Skill/MCP 是否兼容该 CLI。
- 检查任务 RuntimeSnapshot 中冻结的 CLI 版本、路径哈希和能力。恢复时发现漂移会记录诊断事件；缺少 Session 或结构化输出能力会直接阻断。
- MCP 的“配置可解析”、“命令存在”、“运行健康”是三个不同状态；凭据缺失不会被当成可用。

## 任务卡住

不要只看看板文案。打开任务诊断核对：Scheduler 租约、最后心跳、活动 WorkUnit、CLI Session、权限请求和最新失败。暂停/恢复会中断当前外部 Session 并依据持久状态重建调度；不会仅修改页面状态。

## 上报问题时保留

- 任务 ID、发生时间和操作步骤。
- 运行诊断页内容与相关 `runtime.log`。
- `daemon.log` 中同时间段和 API 错误的 request ID。
- `./yanxu db-backups` 输出和设置页 Schema 版本。

日志可能包含用户提交给 CLI 的项目文本，对外发送前应先脱敏。
