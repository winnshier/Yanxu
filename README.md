# 研序 Yanxu

研序是一个本地优先的 AI 研发编排工作台。用户提交需求并确认计划后，系统按项目事实自动组织需求分析、实现、测试、质量门禁、评审和交付；任务可以暂停、停止、恢复和自动重试，全程保留可追溯记录。

研序不是把多个 CLI 简单串成一条提示词。它负责持久化任务状态、管理可延续或独立的 CLI Session、隔离 Git 工作区、执行确定性门禁，并把经过用户确认的项目认知沉淀到独立于代码仓库的 ProjectSpace。

## 当前版本（1.5.0 候选）

1.5.0 候选版面向 macOS，本地开箱即用，不需要登录。1.1–1.5 在原有研发闭环上增加了独立 Run、双 CLI 能力兼容、定时触发、可解释项目记忆和统一控制台：

- Task 与每次真实 CLI Run 已分离；重试、恢复和定点修复会创建新 Run，并保留 Session、工作区、失败分类、心跳、进程事件和重试关系。
- 任务详情可以进入独立 Run 证据查看器，按状态、思考、文本、工具和错误筛选事件，同时查看 Session、现场、恢复建议和 Runtime 日志。
- OpenCode 与 Claude Code 使用独立适配器、进程组停止和任务级能力投影；CLI 路径、版本、模型及必要能力会冻结并在恢复时检查漂移。
- 支持从已确认任务创建一次性或周期定时定义；每次触发产生独立 Task 与 Run，支持休眠补跑、重叠合并、暂停和历史，不自动合并、推送或部署。
- ContextPack 只装载当前有效知识，并记录相关度、命中词、来源任务、版本链以及为什么选择该知识；用户纠正后旧知识退出当前检索。
- 全局工作台已统一为浅色高密度布局，任务条持续展示阶段，项目页区分任务、知识、关联资源与 ProjectSpace 历史，定时配置和能力矩阵使用统一视觉语义。

核心研发能力包括：

- 支持一个项目关联多个本地目录，目录可以是代码、文档或空目录；没有 Git 的目录会在首个相关任务计划确认后初始化本地仓库。
- 内置 5 个通用 Agent Role、6 个研发增强 Agent Role，以及 39 个可投影 Skill；它们提供人员职责和默认能力建议，不决定任务流程，也不要求团队机械覆盖全部角色。
- 支持创建 AI 人员并自由组成团队；人员绑定 Role、CLI、模型和权限模式，团队是规划时的候选人员池，不按 Skill 覆盖率阻断新任务。
- AI 人员可设置默认 Skill/MCP 偏好；规划时只作为推荐，仍需能力已在当前项目启用，且任务确认时按 WorkUnit 冻结。
- OpenCode 与 Claude Code 均已接入统一执行契约；人员和协调器可以选择其中任一可用 CLI，Codex 等其他 CLI 在双主线稳定后再评估。
- Claude Code 使用官方非交互 JSON Schema 通道、可恢复 Session 与任务级权限清单；计划内操作可无人值守，计划外操作在 `dontAsk` 模式下拒绝并交由 Yanxu 重试、重新规划或等待用户处理。
- 能力中心只读发现 OpenCode、Claude Code 和通用 Agent 目录中的标准 Skill/MCP；同名同类型能力自动去重为一个逻辑项，可选择内置、本地或不同 CLI 来源，并按全部、已安装、未安装筛选。
- 所有 Skill/MCP（包括内置项）都可安装、切换来源、卸载和重新安装；卸载会同步停用项目引用、移除人员默认挂载，真实执行前仍会按当前安装状态与 CLI 兼容性复核。
- 标准 Skill 可从本地目录、ZIP 或公开 GitHub 仓库导入；扫描阶段不会执行第三方脚本。导入草稿经安全信息审查后才安装到研序托管目录，再由具体项目显式启用。
- 项目启用的能力写入 ProjectSpace 锁文件；计划按 WorkUnit 选择实际装载的 Skill/MCP，任务确认后冻结内容哈希、版本、人员和执行器，并投影到任务独立的 OpenCode 配置目录，不改写全局 CLI 配置。
- 不同任务可以并行；同一任务的 WorkUnit 串行执行，同一人员、同一 CLI 默认延续 Session，跨 CLI 步骤会显式关闭旧 Runtime，独立评审可显式新开 Session。
- RuntimeSnapshot 同时冻结任务所用 CLI 版本、路径哈希、能力和模型；恢复执行时会检查运行环境漂移与必要能力，并写入统一诊断事件。
- AI 团队的 Role 库支持从本地目录或公开 GitHub 仓库识别 Claude 子代理、OpenCode Agent、GitHub Agent Profile 和纯提示词角色；导入先形成可审查草稿，无法可靠转换的内容只供查看或标记不兼容。
- 外部 Role 的基础指令、责任、兼容 CLI、权限声明、Skill/MCP 依赖、来源、版本和内容哈希可审查；更新后重新进入草稿状态，并提供前后版本变化预览，不会改写运行中任务快照。
- 提交分析后由协调器判断本任务是否需要正式 RequirementSpec；需要时先生成版本化规格，不需要时直接依据用户需求和项目事实规划。用户回答歧义并确认后，需求版本、确认前产物、计划、团队、人员和权限清单一起冻结为运行快照。
- 新任务的 WorkUnit 声明目标、人员、能力需求、读写模式、验证点和会话隔离要求，不强制固定 Artifact；可写单元必须产生真实 Git 变更。
- 下一 WorkUnit 由 ContextPack 按冻结计划、相关产物、项目知识、变更和门禁失败证据组装最小上下文，不需要重读全部历史。
- 创建任务时可选择本地附件；附件通过短期令牌复制到 ProjectSpace 并记录哈希，文本内容按上限进入需求/计划上下文，二进制附件只保留原始证据。
- 规划器会在容量上限内检索关联目录中的相关代码、配置和文档，同时排除常见密钥与敏感路径；歧义回答必须先由规划器吸收到新版计划，之后才能由用户最终确认。
- 通过 Git branch + worktree 隔离任务，已有 staged、unstaged、untracked 内容会冻结为任务基线，不改动用户原工作区和索引。
- 计划确认时会冻结来源工作树指纹；执行前发现用户又修改了来源目录时会停止使用旧计划并要求重新规划，避免在过期事实之上执行。
- 每个成功写入 WorkUnit 都记录逐文件 ChangeManifest；越界或敏感文件改动只记录拒绝事件与文件路径，不会进入 checkpoint，并转为需要重新确认的计划。
- 用户确认的文件范围、只读边界和命令会按步骤编译为可审计 PermissionManifest；标准模式把计划外动作送到调度台，全托管模式自动拒绝未规划动作，两种模式都不能突破敏感文件与高风险操作硬边界。
- 后台任务支持租约恢复、指数退避重试和一次边界内自动重规划；扩大目录、权限、目标或成功标准时必须重新人工确认。
- 质量门禁在计划确认时冻结，并以 argv 直接执行，记录每轮命令、退出码、信号、超时和日志；模型自报成功不能覆盖真实失败，失败证据会退回对应写入单元定点修复。
- 交付时可以保留任务分支自行合并，或由研序预检后合并到任务指定的目标分支；机械性冲突可确定处理，语义冲突会保留现场等待用户，多目录中途失败会反向补偿，合并后还会在临时 worktree 重跑门禁。
- 交付后生成项目知识候选。候选可修订、确认或驳回，修订和确认都会创建新版本并保留 supersedes 链，只有当前有效版本进入全文检索上下文。
- Project Directory Profile 先生成候选版本，由用户确认后才替换当前事实；ProjectSpace 的文档写入与 Git milestone 有独立操作日志，失败不会被静默忽略。
- 每次 ProjectSpace milestone 都会刷新带哈希的 `state/current.json`；SQLite 丢失时可在项目页选择 ProjectSpace 预演并恢复项目、目录、团队引用、任务、计划、附件、Session、权限、变更、门禁、冲突、交付、事件、知识和运行快照。无法恢复的运行现场会安全转为 `STOPPED`。
- 交付结果被用户纠正时会生成新的 TaskVersion；旧需求、计划和证据保留，源自旧版本的候选/有效知识会退出检索，避免继续传播错误经验。
- 用户项目不绑定语言或框架；质量门禁会优先识别已有 Node.js、Python、Go、Rust 或 Makefile 检查命令。

## 运行要求

- macOS
- Node.js 22.0.0 或更高版本
- pnpm（项目不限制 pnpm 主版本；所用版本需要能够读取当前锁文件）
- Git
- OpenCode CLI 或 Claude Code CLI（按实际创建的人员和协调器选择安装；浏览、配置和草稿不要求）

在 Node.js 22 和 24 之间切换后，`./yanxu` 会自动检测并按当前 Node.js ABI 重编译 `better-sqlite3`。

## 一键启动

```bash
git clone <your-fork-or-repository-url>
cd Yanxu
./yanxu
```

脚本会在首次运行时安装锁定依赖，构建前后端，启动本地服务并打开 `http://127.0.0.1:43120`。按 `Ctrl+C` 停止服务。

开发模式：

```bash
./yanxu dev
```

如果文件执行权限在下载过程中丢失，可先运行 `chmod +x yanxu`。

## 首次使用

1. 打开“设置”，检测本地 CLI，执行一次真实 Runtime 启停验证，并选择全局协调模型。
2. 在“AI 团队”中创建人员，可选择已检测的 OpenCode 或 Claude Code、兼容 Role 和模型；也可以先导入并审查外部 Role。
3. 将人员组成一个团队；可以设置一个全局默认团队。
4. 创建项目并选择首个本地目录。ProjectSpace 由研序自动分配，不会放进代码目录。
5. 创建任务，选择项目和团队，提交需求分析。
6. 可先在“能力中心”扫描或导入 Skill/MCP，并在项目的“项目能力”页启用所需能力。
7. 回答歧义问题，检查动态 WorkUnit、执行人员、实际装载能力、读写边界、涉及目录、质量门禁及源/目标分支；保存计划并确认后，系统准备隔离工作区并无人值守推进。
8. 在调度台处理权限、阻塞或交付确认；交付知识需要在项目页单独确认后才会参与后续检索。

## 本地数据

默认数据目录为 `~/.yanxu`：

```text
~/.yanxu/
├── system/app.db             # SQLite 状态、任务、事件、权限和索引
├── capabilities/             # 已安装能力的不可变内容版本
├── imports/                  # 等待审查和安装的外部 Skill 与 Role 草稿
├── projects/<project-id>/    # 每个项目独立的 ProjectSpace 与 Git 历史
├── runtime/tasks/<task-id>/  # task worktree、执行现场、操作日志
└── runtime/logs/             # 本地运行日志
```

ProjectSpace 与用户关联的项目目录是两个概念：前者保存需求、计划、步骤产物、交付报告和知识版本；后者保存实际代码或文档。两边分别使用 Git 追踪。

Daemon 使用单实例锁避免两个本地进程同时调度同一数据库；健康接口会分别报告数据库和 Scheduler 状态。工作台 API 使用本机持久随机会话 Cookie 与 CSRF 令牌，写请求会拒绝跨站来源；文件夹和附件选择使用短期一次性 token，网页不能直接提交任意绝对路径。

临时改变数据目录或端口：

```bash
YANXU_HOME=/path/to/local-data YANXU_PORT=44000 ./yanxu
```

## 安全边界

- 执行器默认只允许在研序准备的隔离工作区内工作。
- 工作台 API 需要 HttpOnly、SameSite=Strict 的本机会话 Cookie；所有修改请求还需要 CSRF 令牌。
- 系统文件夹与附件选择只返回短期一次性 token，真实路径只在本地 Daemon 内解析。
- `.env`、私钥等敏感文件不会进入任务基线，运行规则也拒绝读取常见密钥文件。
- 本机 OpenCode/Claude Code 已配置的 MCP 凭据继续由原 CLI 配置托管；研序只保存定位引用，任务启动时临时注入子进程。第三方扩展自身携带的明文凭据仍禁止安装。
- 默认禁止 `git push`、修改远程仓库、部署、`sudo` 和高风险递归删除。
- 标准权限模式把未预授权动作送到调度台；全托管模式仍保留上述不可突破的硬边界。
- “合并到目标分支”只操作本地 Git，不会推送远程。冲突时保留任务分支并要求用户决定。
